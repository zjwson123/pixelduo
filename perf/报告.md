# 性能冲刺报告：PixelDuo 落地页

**结论：落地页「打开到能用」的 p75 从 6691ms 降到 1493ms，降幅 77.7%**（配对测量，同机同时段
A/B 交替，10 次/组，两个独立口径互相印证）。布局、文案、SEO 字段逐项一致到字节，主线程
从头到尾没有长任务。

- 冲刺前的基线、口径与首屏拆解：`perf/基线.md`
- 每一改动的假设、做法与数字：`perf/实验日志.md`
- 复查用的命令与护栏：`perf/bench/README.md`

## 前后对比

| 操作 | 口径 | 优化前 p75 | 优化后 p75 | 降幅 | 配对测量时段 |
|---|---|---|---|---|---|
| 落地页 `/` | Fast 4G, dpr 1 | 6691.4ms | **1493.4ms** | **77.7%** | 2026-09-26 23:5x（10/10 与 9/10 两组独立口径） |
| 落地页 `/` | Fast 4G, **dpr 2** | 6693.8ms | **2613.8ms** | **61.0%** | 2026-09-27 04:xx（A 10/12、B 12/12） |
| 工作台 `/studio` | Fast 4G, dpr 1 | 630.9ms | 640.3ms | −1.5%（噪声内，见下） | 2026-09-27 05:xx（12/12 两侧） |

**dpr 2 那一行值得单独看一眼**：优化前的基本版**没有 `srcset`**，所以它在 dpr1 和 dpr2 上取的是
同一批原图（6,691ms / 6,693ms，几乎一样）；优化后 dpr2 会去取 2x 档，字节从 738KB 涨到
1.30MB，时间也就从 1493ms 涨到 2613ms —— 这 1.12 秒是**为 retina 清晰度付的钱**，不是退步：
同样的清晰度，基线要传 2.96MB。多出来的部分主要在折线以下（10 张 marquee × 640w + 3 张 how × 840w），
而基线那边折线以下的图**本来**就是按 4K 原图传的。

**工作台那一行要按「没有变化」读，不是「退步 1.5%」**：p75 的 9ms 差异小于同一组内
p50→p95 的 55ms 跨度，而且 p50（627.5 → 631.9）与 p95（683.2 → 667.2）指向相反的方向。
工作台本来就不含 showcase 图片，这次改的东西碰不到它 —— 它在这里的作用是**确认没有连带
损伤**，而不是拿收益。

同一口径下的确定性计数（p75）：

| 计数 | 前 | 后 | 降幅 |
|---|---|---|---|
| 首屏总字节 | 2,957,237 | 737,621 | 75.1% |
| 首屏图片字节 | 1,326,818 | 480,900（hero 275,220 + 折线以下 205,680） | 63.8% |
| LCP | 6708ms（`case1.jpg` 634KB） | 1504ms（`case1-hero-720.webp` 170KB） | 77.6% |
| 请求数 | 28 | 31 | +3（`srcset` 多档位） |
| 主线程长任务 | 0ms | 0ms | — |

**两个独立口径互相印证**：先按 skill 原版口径（每轮新建 browser context）测得
6691.4 → 1493.4ms（10/10 全成功）；后用「复用 context + 每次清缓存」的口径测得
6692.2 → 1489.4ms（9/10）。两者相差 4ms 以内。改用第二种口径的原因见
`perf/bench/README.md`（原口径在这台机器上约 1/6 的轮次会把浏览器网络服务卡死 900s）。

## 副作用检查：折线以下的图反而更快出现了

因为给折线以下的图加了 `fetchpriority="low"`，我专门量了一次「滚到底之后 3 秒，25 张图加载了几张」
（Fast 4G，3 次，结果完全一致）：

| | 滚到底 +3s 已加载 |
|---|---|
| 基线 | **5/25** |
| 优化后 | **17/25** |

基线那边的图太大了，3 秒连 796KB 的首屏都没下完，折线以下基本还是空白；优化后虽然优先级更低，
但每张小了一个数量级，反而先到。**「低优先级」在这里没有换来「更晚出现」**，方向上正好相反。

## 每一步各贡献了多少

| 步骤 | 改了什么 | 计数上的变动 | 效果 |
|---|---|---|---|
| 1 | 15 张落地页图片按**渲染尺寸与长宽比**预生成两档 WebP，配 `srcset`/`sizes` + `fetchpriority` | 首屏图片 1.33MB → 0.48MB；总数 2.96MB → 0.74MB | 6691 → 1493ms（这一条贡献了几乎全部） |
| 2 | hero 的 2x 档从 1440 收到源图分辨率 960 | hero 2x 609KB → 385KB | dpr=2 那一组（见上表） |
| 3 | （被证伪，未采纳）`content-visibility: auto` 推迟折线以下的图 | 折线以下字节 205,680 → 205,680，一张不少 | 0 |

第 1 步为什么能一次拿这么多：这些图从「原图直出」直接跳到「按渲染尺寸裁切 + 现代编码」，
中间没有过渡 —— `case338.jpg` 是 3072×1024 的 3:1 图，塞进 280×350 的 4:5 窗口，等于给用户
传了 11 倍的像素；首屏那张 `case1.jpg` 是 941×1672 的 634KB 原图，而渲染框只有 641×648，
还被 `object-fit: cover` 又裁掉近四成。

## 没做的、和为什么

**1. 折线以下的图仍旧会和 LCP 抢带宽（建议做，但要你拍板）。**
先量了上限：把折线以下 13 张图的请求全拦掉，「能用」p50 从 1487ms 降到 **1072ms** ——
也就是 dpr=1 上最多再拿回 **415ms（28%）**；dpr=2 上折线以下占了 1.30MB 里的约 0.6MB，
这一条带来的收益会更大（尚未单独量）。同时量了一组对照：把所有 showcase 图都拦掉是 **108ms**，
说明 HTML/CSS/JS 在这条路径上根本不在关键路径里，剩下的时间**全部**是图片。

要拿到这 415ms，必须让 SSR 出来的 HTML 里没有 `src`（改成 `data-src` + IntersectionObserver，
或挂载后再赋 `src`），代价是：**关掉 JS 时 marquee 是空的、图片索引依赖 JS 执行**。这是用户
能感知的行为改动，按规矩交给你拍板。我的建议是**做**，并且限制成「等 hero 的图 load 完再
开始加载折线以下」，这样用户滚到那一屏时图早就在了，体感无变化；但那一句「无 JS 时 marquee
是空的」是真实的代价，得你认。

**2. JS 那 233KB（gzip）没有动。**
落地页的关键路径 JS 是 828KB 原始 / 259KB gzip，其中 458KB 那个 chunk 里能认出 react-dom 和
`@sentry/nextjs`。但按上面那组对照，**把图片全去掉后页面 108ms 就可用了** —— 也就是说这
233KB 根本不在「打开到能用」的路径上，动它只能改善 TBT 之类的指标，而实测主线程长任务
是 **0ms**。按「几百行代码只换来几毫秒的，主动提出不做」，这一条我不建议做；如果你想为
**弱网/低端机**再做一层，可以单独开一轮（候选：把 `@sentry/nextjs` 改成有 DSN 时才动态
import —— 但它是错误监控，属于功能改动）。

**3. 静态资源的 `Cache-Control: public, max-age=0` 没动。**
`public/` 下的文件现在每次访问都要回源校验（ETag → 304）。它不影响「打开到能用」这个冷缓存
指标，只影响**回访**：每张图多一个 RTT。候选做法是给 `/showcase/:path*` 加
`Cache-Control: public, max-age=3600, stale-while-revalidate=86400`（文件名不带内容哈希，
所以不能直接上 `immutable`）。收益不大（回访时约 1 个 RTT，Fast 4G 下 20ms），我倾向不做。

## 护栏（每一步都跑）

| 护栏 | 结果 |
|---|---|
| SEO / 文案黄金（title、description、og:*、twitter:*、robots、canonical、h1-h3、全部 16 个链接目标、25 个 alt、81 行可见文本） | **全部一致** |
| 视觉回归（1440 与 390 两种宽度，16 个关键元素的 bounding box + 文档总高度） | **逐项一致**（±1px）；图片以外区域像素差 **0.0000%** |
| 功能冒烟（分割线拖动、语言切换来回、锚点、CTA 目标、图片无损毁、工作台输入与余额、无页面报错） | **两版本结论一致，全过** |
| 棘轮（p75 / 请求数 / 字节数只许降不许升） | 已记在 `perf/bench/ceilings.json`：dpr1 `ready_p75 ≤ 1482.5ms`、31 请求、737,626B；dpr2 `ready_p75 ≤ 2610.9ms`、31 请求、1,302,006B |

棘轮的用法（改动后跑一次，变差就非零退出）：

```bash
python3 perf/bench/bench.py --url http://localhost:3000/ --ready "$LANDING_READY" \
  --runs 10 --profile fast4g --dpr 1 --out perf/bench/now.json
python3 perf/bench/ratchet.py check --result perf/bench/now.json \
  --ceilings perf/bench/ceilings.json --label landing-dpr1 --metric bytes_total --tolerance 0
```

计数类指标（`requests_p75` / `bytes_total_p75`）用 `--tolerance 0`：它们是确定性的，没有噪声
可讲；`ready_p75` 用默认的 5%。

视觉护栏抓到过一次真问题：给三张 `.how-cell img` 加 `width`/`height` 属性后，`.how-grid`
在 1440px 下高了 41px（那条 CSS 只有 `aspect-ratio`、没有 `height`，属性会变成实际使用的高度）。
这个改动在页面底部，肉眼扫一遍看不出来 —— 已回退，几何恢复逐项一致。

## 上线清单与回滚

**上线由你批准。** 本冲刺没有推送、没有部署、没有改任何 DNS/CDN/托管平台配置。

要发的文件（提交时逐个点名，不用 `git add -A`）：

| 文件 | 说明 |
|---|---|
| `components/landing.tsx` | 图片标记改成 `srcset`/`sizes` + 优先级属性 |
| `scripts/gen-image-variants.ts` | 新增：变体生成器（可重复运行） |
| `public/showcase/*.webp` | 新增：30 个变体（15 张图 × 2 档），约 2.2MB |
| `.gitignore` | 只忽略 `perf/bench/*.json`、`perf/shots/`、`perf/raw/` |
| `perf/**` | 本冲刺的简报/基线/实验日志/报告/工具 |

**上线前还要做两件事**：
1. 构建镜像时把 `npx tsx scripts/gen-image-variants.ts` 挂到构建前（或确认 `public/showcase/*.webp`
   已进 git —— 现在是进了的，脚本只是让源图换掉之后能一键重生成）。
2. **量一次线上旧版**做对照（本冲刺无法做：`pixelduo.ai` 无 DNS 解析，没有可测的线上环境）。

**回滚**：`git revert <commit>` 后重新构建部署。图片全部是新增文件 + 一处标记改动，回滚是纯
revert，没有数据迁移、没有外部配置。

**风险**：
- 图片观感是**你**要拍板的那一项。变体的裁切区域与 CSS `object-fit: cover` 完全一致（几何
  回归证明布局零变化），差异只在重新编码：图片区域像素差 5.2%（1440px）/ 4.6%（390px）。
  已经给你备好 1:1 的前后对比图（**没进 git**，在本机 `perf/shots/` 下）：

  | 文件 | 看什么 |
  |---|---|
  | `compare-hero.png` | 首屏对比图 641×648 的 1:1 上下叠图：上=634KB 原图，下=170KB WebP |
  | `compare-marquee.png` | marquee 一条 900×350 的 1:1 上下叠图：上=1050KB 原图，下=19KB WebP |
  | `base-1440.png` / `new-1440.png` | 整页前后截图（1440px） |
  | `base-390.png` / `new-390.png` | 整页前后截图（390px 手机） |

  我看过 `compare-hero.png`，在渲染尺寸下两条几乎分不出来；**但这是你的产品，请你自己再看一眼**。
- 2x 档只到 960：源图本来就只有 941/600px 宽，所以 retina 上的清晰度不会比现在差，
  但也不会更好 —— **要真正更清晰得换源图**，那是另一件事。
- 折线以下的图片数量没变，只是每张小了一个数量级；`srcset` 让请求数从 28 增加到 31。
