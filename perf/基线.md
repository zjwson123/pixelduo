# 基线：PixelDuo 落地页与工作台

测量日期 2026-09-26/27，基线版本 `db216b2`（工作区干净）。
两个服务同时起着，测量时按 A/B 交替配对跑：基线在 `:8123`（用 HEAD 单独 `next build` 出来的
worktree），优化版在 `:3000`。

## 口径

- **主口径 Fast 4G**：往返 20ms、下行 4Mbps、上行 3Mbps，由 CDP `Network.emulateNetworkConditions`
  对所有请求生效（含 `127.0.0.1`）。冷缓存（每次新建 browser context + `Network.setCacheDisabled`）。
- 每组 10 次，报 p50 / p75 / p95。**dpr 1 与 dpr 2 各测一组** —— 落地页的对比滑块在 retina
  上会走 `srcset` 的 2x 档，只看 dpr=1 会完全看不见 2x 那一档的体积代价（实测 2x 档一度占了
  首屏图片字节的 61%）。
- 生产构建（`next build` + `next start`），不是 `next dev`。压缩为 Next 默认 gzip（线上 Caddy 的
  `encode gzip` 叠在其外，所以本地量到的 gzip 字节与线上同档）。

## 「能用」的定义

| 操作 | 终点 | 判定 |
|---|---|---|
| 打开落地页 `/` | 首屏标题可见 + 对比滑块两张图**都解码完成** + 主 CTA 在 | 见 `perf/bench/run.sh` 的 `LANDING_READY` |
| 打开工作台 `/studio` | 提示词输入框可见可输入 + `/api/me` 已返回（余额已渲染） | 见 `STUDIO_READY`，另加打字校验 |

落地页把「两张对比图解码完成」写进判定，是因为这个页面的价值就是让人看见产品长什么样；
图片没到就还不算能用。工作台要求 `/api/me` 返回，是为了挡住「没水合的空壳也算达标」。

## 首屏拆解（落地页，Fast 4G，冷缓存）

LCP 元素：

```
{ tag: IMG, src: /showcase/case1.jpg, startTime: 6696ms, size: 415037 }
```

`size` 415037px² ≈ 641×648 —— 正是 `.compare` 渲染框的面积，也就是说 **LCP 就是首屏那张对比图**。

按类型（传输字节，到「能用」为止）：

| 类型 | 字节 | 占比 |
|---|---|---|
| img | 1,326,818 | 55.7% |
| link（含 Next 注入的图片 preload） | 808,266 | 34.0% |
| script | 233,196 | 9.8% |
| fetch（`<Link>` 预取） | 7,233 | 0.3% |
| navigation（HTML） | 4,657 | 0.2% |
| **合计** | **2,380,170** | |

排名靠前的请求：

| 字节 | decoded | start | end | 类型 | 资源 |
|---|---|---|---|---|---|
| 634,335 | 634,035 | 32 | 6678 | link | `/showcase/case1.jpg` ← LCP |
| 434,762 | 434,462 | 133 | 6475 | img | `/showcase/case355.jpg` |
| 370,916 | 370,616 | 133 | 4892 | img | `/showcase/case390.jpg` |
| 238,586 | 238,286 | 133 | 5739 | img | `/showcase/case402.jpg` |
| 220,081 | 219,781 | 133 | 2987 | img | `/showcase/case373.jpg` |
| 162,842 | 162,542 | 33 | 1791 | link | `/showcase/case225.jpg` ← 对比图右半 |
| 144,048 | 458,276 | 33 | 1762 | script | `/_next/static/chunks/3kn9k22r4oh4c.js` |

两个可以直接说出来的结论：

1. **首屏的两张对比图是 796KB 的原图直出**（`case1.jpg` 941×1672 / 634KB，`case225.jpg` 600×900 / 162KB），
   而渲染框只有 641×648，并且 `.compare` 是 `object-fit: cover` + 固定 `aspect-ratio: 4/4.4` ——
   竖向被裁掉近四成，那些像素用户永远看不到。
2. **折线以下的 marquee 图在第 133ms 就和 LCP 抢带宽**。它们标了 `loading="lazy"`，但 Chrome 在
   快速连接上的懒加载阈值有 1250px，而 `.strip-sec` 从 ~900px 就开始了 —— 阈值根本没拦住。
   最有代表性的是 `case338.jpg`：3072×1024 的 3:1 图塞进 280×350 的 4:5 窗口，等于给用户传了
   11 倍的像素。

## 确定性计数（当每步的闸门用）

| 计数 | 基线 |
|---|---|
| 首屏关键路径 JS（gzip） | 259,262 B（原始 828,028 B，10 个 chunk） |
| 首屏 CSS（gzip） | 6,716 B |
| 首屏请求数 | 27–28 |
| 主线程长任务（>50ms）总时长 | **0 ms** |
| 首屏图片字节 | 1,326,818 B（其中两张对比图 796,577 B） |

长任务为 0 是个重要事实：**这个页面没有任何主线程问题，从头到尾是带宽问题**。所以后面的
每一步都盯着「首屏要传多少字节」，而不是「拆多少 JS 逻辑」。

## 线上

**没有。** `pixelduo.ai` / `www.pixelduo.ai` 都无 DNS 解析（curl 退出码 000），也就是说这个项目
目前没有对外的部署，拿不到 CrUX 真实用户数据。这里如实写「没有」，不用 Lighthouse 分数顶替：
Lighthouse 是实验室数字，不承担「真实用户有多快」的结论。

同样地，由于没有线上版本，「上线前先量一次线上旧版」这一步在本冲刺里无法执行 —— 上线后必须
补做（用同一台机器、同一条网络、同一个判定表达式，另加一个对照站排除测量机自身的网络）。
