# 实验日志

一条改动一条记录，一个改动一个 commit。每条的判据都是：棘轮与护栏全绿 **且** 配对测量确实变快，
否则回退。

---

## 实验 1：落地页 15 张图换成「按渲染尺寸预生成」的 WebP + srcset

**假设**：首屏 2.38MB 里 1.9MB 是图，LCP 就是 `case1.jpg` 那张 634KB 的原图；把图按**实际渲染尺寸**
重新生成并编码成 WebP，能把首屏图片字节降一个数量级，`能用` p75 相应下降。

**做法**：
- 新增 `scripts/gen-image-variants.ts`（sharp，构建期预生成、产物进 git）：按每个槽位**渲染出来的
  长宽比**居中裁切，再编码成两档 WebP。因为 CSS 那边本来就是 `object-fit: cover` + 固定
  `aspect-ratio`，裁掉的正是用户永远看不到的部分，所以这一步是无损观感的。
  槽位与实测渲染尺寸：`.compare` 641×648（4:4.4）、`.mq-item` 280×350（4:5）、`.how-cell img` 391×245（16:10）。
- `components/landing.tsx`：`srcset` + `sizes`、`fetchpriority="high"`（LCP 图）、
  `fetchpriority="low"` + `loading="lazy"` + `decoding="async"`（折线以下）。

**确定性计数**：

| 计数 | 前 | 后 |
|---|---|---|
| 首屏图片字节 | 1,326,818 | 205,680 + 275,220（两张 hero） |
| 其中 LCP 那张 | 634,035 | 170,212 |
| 首屏总字节 | 2,957,237 | 737,616 |
| 请求数 | 28 | 31 |
| 主线程长任务 | 0 ms | 0 ms |

请求数从 28 涨到 31：`srcset` 让浏览器多取了几张 1x 档，且 2x 档不再被浪费。

**结果**：配对测量（同机同时段 A/B 交替，10 次/组）`能用` p75 **6691.4ms → 1493.4ms，降 77.7%**。

**回退过一版**：第一版给三张 `.how-cell img` 加了 `width`/`height` 属性，视觉回归立刻报出
`.how-grid` 高了 41px（1440px 视口）——因为那条 CSS 只有 `aspect-ratio`、没有 `height`，
属性会变成实际使用的高度。去掉属性后几何逐项一致。这正是「先建护栏再改代码」的价值：
这个改动在页面底部，肉眼扫一遍是看不出来的。

## 实验 2：hero 的 2x 档从 1440 收到源图分辨率 960

**假设**：`.compare` 渲染宽 641px，DPR2 需要 1282px，于是浏览器会挑 1440 那一档 —— 但源图
`case1.jpg` 只有 **941px** 宽（`case225.jpg` 更只有 600px）。1440 档是纯插值，多传 224KB 换不到
任何真实细节。

**做法**：hero 档位 `[720, 1440] → [720, 960]`。

**确定性计数**：hero 2x 档 383KB + 226KB = **609KB → 385KB**（−224KB）。

**结果**：见配对测量的 dpr=2 组（本条的收益在 dpr=1 上看不见 —— 这正是给 bench 加 `--dpr` 的原因）。

## 实验 3（被证伪）：用 `content-visibility: auto` 推迟折线以下的图

**假设**：`.strip-sec` 的 marquee 图在第 133ms 就和 LCP 抢带宽，如果给这两个 section 加
`content-visibility: auto` + `contain-intrinsic-size`，浏览器会不会顺带不加载屏外的图，
从而不用写一行 JS 就拿到收益。

**结果**：**没有**。三种配置下折线以下图片字节都是 205,680B，一张不少地全下。这个方向作废，
不引入 CSS（避免为了零收益增加布局风险）。

## 实验 4（只测不做，交用户定）：把折线以下的图推迟到 hero 之后

**假设**：折线以下 13 张图（205KB）在 hero 还没下完时就开始抢带宽，占掉「打开到能用」期间
约 40% 的带宽。让它们等 hero 加载完再开始，能拿回这段时间。

**先量上限再动手**：用 Playwright 直接拦掉这些请求，测出来的 p50 是 **1072ms**（现状 1487ms），
也就是**天花板 415ms（28%）**。同时测了一组「所有 showcase 图都拦掉」的对照：**108ms** ——
说明 HTML/CSS/JS 在「能用」这条路径上根本不在关键路径里，剩下的时间**全部**是图片。

**为什么不直接做**：它必须让 SSR 出来的 HTML 里没有 `src`（`data-src` + IntersectionObserver，
或者挂载后才赋 src），代价是：无 JS 时 marquee 是空的、图片的抓取依赖 JS 执行。
这是用户能感知的行为改动，按规矩交给用户拍板，附上了 415ms 的实测数字。
